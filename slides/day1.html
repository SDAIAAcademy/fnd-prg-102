What goes wrong. A space splits words: cat field notes.txt asks for two files. Quotes keep one word: cat "field notes.txt".

Commands to know: pwd (where am I), ls -a (what is here), cd (go), . (here), .. (one up).

Ask: "If I move the whole folder to another disk, which of these lines still work?" The relative ones inside the folder do; an absolute path written into a script breaks. That is the fault in lab 1.1.

Windows note: Git Bash shows C: as /c/. Paths in scripts use forward slashes everywhere.

Looking round without a file browser

find lists what matches, ls -S orders by size, du adds sizes up

find visits -name '*.csv'            # every CSV under visits/, at any depth
find visits -name '*.csv' | wc -l    # how many
ls -S visits/*.csv | head -n 3       # the three largest
du -h visits                          # the size of the folder, human-readable
Quote the pattern. '*.csv' in quotes reaches find as a pattern; without quotes the shell may expand it first, in the current folder.

Demonstrate on any folder of your own, not on the lab's logs: the lab asks for the November count and the largest October log. Ask why two files with the same number of lines could differ in size (line endings, longer numbers). Leave the answer to the lab.

Permissions

Ten characters say who may read, write or run a file

-rw-r-----  1 analyst field  612 visits.csv
drwxr-xr-x  2 analyst field 4096 archive
PartIn -rw-r-----
Type- a file (d a folder)
Ownerrw- read, write
Groupr-- read
Everyone else--- nothing
  • r read, w change, x run a file or enter a folder
  • chmod u+x run.sh lets the owner run it as ./run.sh
  • chmod go-r secret.env takes reading away from group and others
  • A key file is readable by its owner only

The example is a pattern, not output from the lab. On Git Bash for Windows, ls -l shows approximate bits because Windows files do not have these permissions; that is why lab 1.1 supplies a listing taken in the shape Linux prints. On the provided Linux workspace the real thing works.

A script that works here only

A script that names your folder works on your computer only

Tied to one computer

cd /mnt/share/visits
wc -l *.csv

Runs only where that folder exists.

Tied to itself

cd "$(dirname "$0")/visits"
wc -l *.csv

$0 is the script's own path; dirname keeps its folder.

Single quotes stop the substitution. '$(dirname "$0")' is printed as it is; double quotes let $( ) run and still keep spaces in one word.

This is the pattern the lab asks for, on a different folder. Run both versions from another folder to show the first failing with "No such file or directory".

Streams

Every program has one input and two outputs

stdin (0)

What the program reads: the keyboard, a file after <, or the previous program after |.

stdout (1)

The result. > writes it to a file, >> adds to the end, | hands it on.

stderr (2)

Errors and progress. 2> sends them to a file; they do not go down a pipe.

wc -l visits/*.csv > lines.txt 2> errors.txt

Show that an error from a misspelt file name still appears on screen when only stdout is redirected. Ask: "Where should a script print its error messages?" (stderr, so they never end up inside the result file). Lab 1.3 needs this.

The filters

Six small programs cover most counting questions

CommandDoes one thing
grep 'ERR' · grep -v '^#'keeps the lines that match · that do not match
cut -d' ' -f2keeps field 2 of each line, fields split by a space
sort · sort -rnorders lines · by number, largest first
uniq -c · uniq -dcounts runs of equal neighbours · prints each repeated line once
wc -l · grep -c .counts lines · counts lines that are not empty
head -n 3 · tail -n +2the first three lines · everything from line 2 (skip a header)

Each tool reads lines and writes lines, which is why they join. awk appears once, in the stretch: say it is a small language, worth learning later.

Build it one stage at a time

Add one stage, look at the output, then add the next

cat visits.log | head -n 3                           # 1 · look first
grep -v '^#' visits.log | head -n 3                  # 2 · drop comments
grep -v '^#' visits.log | cut -d' ' -f3 | head -n 3  # 3 · keep the technician code
grep -v '^#' visits.log | cut -d' ' -f3 | sort | uniq -c | sort -rn | head -n 3
Read a pipeline left to right as a sentence: "lines that are not comments, their third field, sorted, counted, largest count first, top three".

Demonstrate live on a short log of field visits you type in front of the room (five lines with a comment line and technician codes T1 to T3); do not use the station logs, whose counts are the lab. The habit to teach: head after every new stage.

The rule people forget

uniq only sees neighbours, so sort first

Without sort

T1
T2
T1
$ uniq -c
  1 T1
  1 T2
  1 T1

With sort

$ sort | uniq -c
  2 T1
  1 T2

Ask the room to predict the left output before you reveal it. This one mistake gives plausible but wrong counts, which is worse than an error.

What you cannot see

A file written on Windows ends each line with an extra character

  • Linux and macOS end a line with LF; Windows programs often write CR LF
  • The CR sticks to the last field: OK and OK\r are two words to sort
  • cat -A shows it as ^M; file names the line endings
  • tr -d '\r' removes it

The same pipeline, two answers

Git Bash's grep on Windows drops the CR from its output; grep on Linux keeps it. A pipeline can be right on one machine and wrong on the next: the theme of the whole course.

This difference was measured when the course was built: on Git for Windows, grep and awk drop the CR; cut keeps it; grep -U keeps it too. Do not say which station's log has CR LF: lab 1.2 finds it.

Keep the pipelines

A pipeline you will run again belongs in a script

#!/usr/bin/env bash
# Counts over the field visits. Run: bash visit_counts.sh > visit_counts.txt

echo "== V1 visit lines (no comments)"
grep -v '^#' visits.log | grep -c .

echo "== V2 visits per technician"
grep -v '^#' visits.log | cut -d' ' -f3 | sort | uniq -c
The echo lines are labels. They make the output readable by a person and by a check.

Input from outside

A script takes its folder as an argument, with a variable as the fallback

grep -v '^#' "$DIR"/visits.log | grep -c .
You runDIR is
bash visit_counts.sh marchmarch

VAR=value command sets the variable for that one command only. export VAR=value sets it for every later command in this shell. Show env | grep VISITS before and after.

Did it work?

Every command ends with a number: 0 means it worked

grep -q T9 visits.log; echo $?  # 1: no match
ls nowhere; echo $?     # 2: an error
false | true; echo $?   # 0: last counts
set -o pipefail
false | true; echo $?   # 1: any failure
  • $? holds the code of the last command
  • set -e stops the script at the first failing command
  • set -u stops on a variable that was never set
  • set -o pipefail makes a pipeline fail when any stage fails
Pick your own code for "bad input". Many tools use 2; say it in the script's usage line.

Run the left column live. The third line surprises people: without pipefail, a pipeline reports only its last command. A script that another program or a pipeline calls must say "I failed" through its exit code, not only in words.

A clear failure

Stop early, say what is missing on stderr, and return a non-zero code

#!/usr/bin/env bash
set -euo pipefail
DIR="${1:-${VISITS_DIR:-}}"
if [ -z "$DIR" ] || [ ! -f "$DIR/visits.log" ]; then
  echo "usage: bash visit_counts.sh <folder> (or set VISITS_DIR)" >&2
  exit 2
fi
Why it matters for reproduction. A peer following your README sees "set VISITS_DIR" instead of an empty result that looks like zero visits.

Ask what the script printed before this guard when the folder was wrong: zero, which reads like a real answer. Lab 1.3 applies this to counts.sh with AIR_LOGS.

Remote login

An SSH key pair: the public half opens the door, the private half never leaves you

1 · Makessh-keygen -t ed25519 writes key and key.pub
→
2 · Givethe .pub file to the server or the Git host
→
3 · Provethe server checks a signature made with the private key
→
4 · Checkcompare fingerprints: ssh-keygen -lf key.pub
The private key is a secret. Protect it with a passphrase, readable by you only, never in a repository.

Ed25519 is the default type of current OpenSSH ssh-keygen (OpenBSD manual page). The fingerprint is how you check, by reading it aloud or comparing it on the host's page, that the key on the server is yours.

Sources: ssh-keygen(1) and ssh_config(5), OpenBSD manual pages.

A host entry

One entry in a config file saves typing and picks the right key

Host field-server
    HostName 198.51.100.7
    User technician
    IdentityFile keys/field_key
    IdentitiesOnly yes

ssh -F ssh_config field-server now logs in as technician with that key only. 192.0.2.0/24 and 198.51.100.0/24 are address ranges reserved for examples.

IdentitiesOnly stops ssh from offering every key it can find, which some servers count as failed attempts. The lab writes the same kind of entry for the lab workspace; logging in needs the provided workspace and the trainer adding the public key.

What a commit is

A commit is a snapshot with a parent, an author, a message and an id

  • The snapshot: every tracked file as it was
  • The parent: the commit it follows (two for a merge)
  • The id is a hash of all of it: change anything, get a new id
  • So history is a chain you can check, and rewriting it changes every id after the change
git log --format='%h %p %s'
# id      parent   message

The id depends on the author and the time too, which is why two participants who type the same commands get different ids. The lab kit fixes authors and dates so its practice repositories have the same ids for everyone. Keep this in mind for Day 3: cleaning a key out of history changes ids.

What a branch is

A branch is a name that points at one commit, and HEAD says which name you are on

o---o---o   <- main <- HEAD
         \
          o   <- draft
  • Pro Git calls a branch "a lightweight movable pointer" to a commit
  • A new commit moves the branch HEAD points at, and only that one
  • Creating a branch writes one small reference: it is cheap
  • git switch draft moves HEAD; the next commit moves draft

Draw it on the board as you speak. Arrows in the graph point from a commit to its parent, which is the opposite of time. Sources: Pro Git, "Branches in a Nutshell".

Worked example

Draw first, run second, compare third

git commit -m "A"        # on main
git branch notes
git commit -m "B"        # still on main
git switch notes
git commit -m "C"
        B   <- main
       /
o--A--+
       \
        C   <- notes <- HEAD

main reaches 3 commits (the first, A, B); notes reaches 3 (the first, A, C); 4 commits in all.

Ask the room to draw it on paper before you press. This is a different sequence from the lab's three; the supervised check asks for five more like it, drawn by hand.

Reading Git's drawing

git log --graph draws the same graph on its side

git log --oneline --graph --all
* 3c1d0e2 (HEAD -> notes) C
| * 9b7a4f1 (main) B
|/
* 5e2a8c3 A
* 1f0b6d9 First commit
  • Newest at the top; each * is a commit; the lines are parent links
  • --all shows every branch, not only the one you are on

The ids here are illustrative, not from a run. Ask: "Which commit is the last both branches share?" (A).

Checkpoint

How many commits does main reach?

A new repository gets one commit on main. Then: git branch fix, two commits on main, git switch fix, one commit. How many commits does main reach, and how many does the repository hold?
