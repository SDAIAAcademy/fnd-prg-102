Session 1

Branches, merges and conflicts

  • Tell a fast-forward from a merge commit on a graph
  • Read conflict markers and keep both changes where both are right
  • Push, fetch and read origin/main as the hub's last known state
01
Two kinds of merge

If main has not moved, Git just slides it forward; if it has, Git makes a merge commit

Fast-forward

before:  o--o  main
              \
               a--b  topic
after:   o--o--a--b  main, topic

No new commit; main points where topic does.

Merge commit

before:  o--o--m  main
              \
               a--b  topic
after:   o--o--m---M  main
              \   /
               a-b   topic

M has two parents: m and b.

Ask the room which kind each merge of lab 2.1 will be before they run it: they can tell from the graph alone. --no-ff forces a merge commit even when a fast-forward is possible; hosts often do that for pull requests so the request stays visible in history.

Remotes

origin/main is your clone's memory of the hub, updated only when you talk to it

CommandYour mainorigin/mainWorking files
git fetchstaysmoves to the hub'sstay
git merge origin/mainmovesstayschange
git pullmovesmoveschange
git pushstaysmoves to yoursstay

git pull is fetch followed by merge (or rebase, if configured). Fetch first when you want to look before anything changes.

The hub in the labs is a bare repository on your own disk; a class host such as Forgejo, Gitea, GitLab or GitHub is the same thing on a server, with pages and permissions around it.

When Git stops

A conflict means both sides changed the same lines, and only a person knows the answer

  • Git merges changes to different lines by itself
  • When both sides changed the same or touching lines, it writes both and stops
  • The merge waits, half done, until you resolve, git add and git commit
  • git merge --abort puts everything back as it was

Not an error

A conflict is a question: "both of you changed this, which text is right?" The answer is often a third text that keeps both intentions.

Say that "touching" matters: changes on two adjacent lines also conflict, because Git cannot tell whether they depend on each other.

Reading the markers

Between the markers, the top is your branch, the bottom is the one coming in

Visits: every two weeks
<<<<<<< HEAD
Inlet cleaned at every visit, photo before and after
=======
Inlet cleaned at every visit; fan checked
>>>>>>> field-checks

A resolution that keeps both

Inlet cleaned at every visit; fan checked; photo before and after

A resolution that loses one

Taking one side whole (--ours or --theirs) when both changes were wanted.

The example is a field-visit plan, not the report template of the lab. After editing: grep -n '^<<<<<<<' file prints nothing, then git add and git commit.

Step by step

Five steps resolve any conflict

1 · Seegit status lists the files
→
2 · Readboth sides and why each changed
→
3 · Writethe text that keeps both intentions
→
4 · Testno markers left; it still runs
→
5 · Recordgit add, git commit

Step 2 is where people skip: read the commit messages of both sides (git log --merge) to learn why each changed the line.

Checkpoint

What does this merge leave behind?

A branch fix has three commits. Nobody committed to main since fix started. On main you run git merge fix. What is in the history now?

The same three commits; main now points at the last one
Three commits and a new merge commit with two parents
One new commit holding the three changes together
Six commits: the three, and a copy of each on main
Why. main is an ancestor of fix, so Git fast-forwards: it moves the pointer and makes no commit.

Answer: A. Ask what git merge --no-ff fix would have added (a merge commit).

Session 2

Pull requests and review etiquette

  • Open a small pull request from a branch with a title that says what changes
  • Write review comments that name a line and a reason, and answer them with commits
  • Resolve a conflict on your own branch before the merge
02
A team's main

On a team, main changes only through a reviewed pull request

1 · Branchone change, one branch
→
2 · Pushthe branch to the host
→
3 · Requestopen a pull request with a clear title
→
4 · Reviewcomments, answers, approval
→
5 · Mergeinto a protected main
Protected branch. The host refuses direct pushes and merges without the required approvals (Gitea and Forgejo call it branch protection; GitLab and GitHub have the same).

Gitea's documentation: protected branches "prevent unwanted changes by enforcing push and merge policies". Set it on the class host before the session: protect main, one approval required. In the kit, the hub's server-side hook refuses pushes to main, and lab.py pr merge is the only way in. Sources: Gitea, Protected branches; Forgejo user guide.

Size

A small request gets a real review; a large one gets a rubber stamp

  • One purpose per request: "Add the rule on comment lines", not "various fixes"
  • A title that says what changes; a description that says why and how to check it
  • Commits that each make sense on their own
  • Open it early as a draft when you want direction, not approval

For the reviewer

If you cannot say in one sentence what a request changes, ask the author to split it before you review line by line.

Ask the room for the largest change they ever had to review. The lesson is practical: reviewers stop reading long diffs, and that is how mistakes reach main.

Review etiquette

A useful comment names a line, a reason and a way forward

CommentWhy it helps or not
"Looks good"Says nothing the author can act on
"This is wrong"No line, no reason, no suggestion
"visit_plan.md line 6: the photo rule repeats line 2; keep one, so they cannot disagree"Line, reason and a fix the author can accept or answer
"Question: is the fan check every visit or monthly?"Marked as a question, not a demand

Comment on the change, not the person. Mark what blocks the merge and what is a suggestion. The author answers every comment, with a commit or a reason, before resolving it.

Answering a review

Answer a comment with a commit on the branch, then mark it resolved

git switch field-checks
# edit visit_plan.md as the comment asked
git commit -am "Keep one photo rule, as the review asked"
git push                     # the request shows the new commit
An approval belongs to a commit. When the branch changes after an approval, the reviewer reads the new commits and approves again; hosts can be set to dismiss stale approvals.

In the kit, lab.py pr resolve refuses until the branch has moved since the comment, and pr merge refuses an approval given on an older commit. The class host does the same when "dismiss stale approvals" is set.

When the request no longer merges

The author brings main into the branch and resolves the conflict there

git fetch origin
git merge origin/main
# resolve, then:
git add visit_plan.md
git commit
git push
  • The author knows the change best, so the author resolves
  • main never holds a half-resolved state
  • The reviewer sees the resolution as a commit and reviews it
  • Some teams rebase the branch instead; never rebase a branch others share

In lab 2.2 the second request conflicts after the first is merged. Make sure the second author does this, not the reviewer.

Checkpoint

Which comment should the author act on first?

A request changes how the field team's visit plan is checked. Four comments arrive. Which is the most useful review comment?

"LGTM, merging"
"I don't like this approach"
"While you are here, please rewrite the whole planner"
"Line 12: the visit interval is set here and in the README; read it from one place"
Why. It names the line, gives the reason (two copies can disagree) and suggests a fix within the request.

Answer: D.

Undoing mistakes

Undoing

Pick the undo by where the mistake is

The mistake isUndo withChanges history?
in a file, not stagedgit restore fileno
staged by mistakegit restore --staged fileno
in the last commit, not pushedgit commit --amendyes, one commit
in commits not pushedgit reset to an earlier commityes
in a commit already pushedgit revert its idno: adds a commit

The column on the right is the safety rule: rewrite only what nobody else has. git-revert's documentation: it records "new commits to reverse the effect of some earlier commits". Sources: git-restore, git-reset, git-revert documentation.

reset, three ways

reset moves the branch; the flag decides what happens to your files

--soft

The branch moves back; the undone changes stay staged.

--mixed (default)

The branch moves back; the changes stay in your files, unstaged.

--hard

The branch moves back; your files are made to match. Uncommitted work is lost.

Before --hard, run git status. A file you never committed cannot come back from the reflog.

git-reset's documentation: it sets "the current branch head (HEAD) to point at" the commit you give. Demonstrate with HEAD~1 on a scratch repository.

The safety net

The reflog remembers where your branches and HEAD have been

git branch -D field-checks          # deleted by mistake
git reflog | head -n 5
# 4c2e9a1 HEAD@{2}: commit: Check the fan at every visit
git branch field-checks 4c2e9a1     # back
  • Local only: each clone has its own reflog, and the hub's is not yours
  • Entries expire after a while (gc.reflogExpire): a net, not a backup

git-reflog's documentation: reflogs "record when the tips of branches and other references were updated in the local repository". The id shown is illustrative.

Checkpoint

Which undo keeps everyone's clone working?

Yesterday you pushed a commit that set the visit interval to 90 days instead of 14. Three teammates have pulled since. How do you undo it?

git reset --hard to the commit before it, then push --force
git revert the commit, then push
git commit --amend, then push
git restore the file, then tell the team
Why. Revert adds a commit that reverses the change, so the shared history only grows and nobody's clone is broken.

Answer: B.

Session 4

Virtual environments and lock files

  • Explain why a project runs on one machine and fails on another
  • Declare dependencies and lock them with an environment manager
  • Rebuild a fresh environment from the lock and compare the output
04
Why it ran here

"It runs on my laptop" means the laptop holds something the repository does not

  • A package installed once, long ago, and never written down
  • A version that happened to be current that month
  • A folder that exists on one disk
  • An output folder created by hand
  • A Python version, a setting, a variable in a profile

The test

A clean clone in a fresh environment. uv run --isolated builds a fresh environment from the declaration alone on your own laptop; a colleague's machine or a container gives the real thing.

Ask the room for their own "worked on my machine" story. Lab 2.4 has four of these faults planted; do not list which.

Two files, two jobs

The declaration says what is acceptable; the lock says exactly what was installed

[project]
name = "visit-planner"
requires-python = ">=3.11"
dependencies = [
    "tabulate>=0.9",
]
  • pyproject.toml: the packages and the range of versions you accept
  • uv.lock: every package, indirect ones included, at one exact version, with hashes
  • uv's documentation calls the lock universal and says it "should be checked into version control"

Sources: uv, Structure and files. Poetry (poetry.lock) and pip-tools (requirements.txt from pip-compile) are the same idea with other files: the course names them as interchangeable examples.

Environments

A virtual environment keeps one project's packages away from every other project

System Pythonshared by everything; never install into it
→
.venv/ per projectits own packages, rebuilt from the lock
→
Ignored by gitthe folder is rebuilt, never committed

uv sync makes .venv/ match the lock; uv run runs a command inside it.

The environment is disposable: deleting .venv and running uv sync --locked again must give the same result. That is what lab 2.4 tests.

The commands

Five commands take a project from undeclared to locked

uv init --bare --name visit-planner --python 3.11   # a pyproject.toml, nothing else
uv add tabulate                                    # declare it, resolve, write uv.lock
uv python pin 3.13                                 # .python-version
uv sync --locked                                   # build .venv exactly from the lock
uv run python planner.py                           # run inside it
--locked refuses to change the lock. uv's documentation: "If the lockfile is not up-to-date, uv will raise an error instead of updating the lockfile."

Source: uv, Locking and syncing. When --locked refuses, someone changed pyproject.toml without locking: run uv lock, read the diff, commit both.

Checkpoint

What does the lock add?

A planner project declares tabulate>=0.9. A colleague installs it a year later from the declaration only and gets different output. What would a committed lock file have given them?

The exact versions and hashes the author installed, indirect packages included
A second list of the same package names
A copy of the packages' code inside the repository
The newest versions at the time of installing
Why. >=0.9 allows any later release; the lock records the one resolved, so a rebuild installs that again.

Answer: A.

Day 2 · wrap-up

Three things to keep

Small and reviewed

One purpose per request; comments name a line and a reason; answers are commits.

Rewrite only what is yours

Amend and reset before a push; revert after it.

Declare, lock, rebuild

If a fresh environment from the lock does not reproduce the result, the repository is missing something.
