Session 1

One command to rebuild and run

  • Keep data and outputs out of the repository and say where they come from
  • Write one documented command that rebuilds and checks the result
  • Test a README by following it in a clean clone
01
What a repository holds

Code and the recipe go in; data, outputs and environments stay out

In the repository

Source, pyproject.toml and the lock, the container definition, the rebuild command, the README, small expected checksums, a .env.example.

Out of it

Raw data (it has its own home and its own rules), outputs (rebuilt), .venv/ (rebuilt), .env (secret), caches.

.gitignore does not untrack. A file already committed stays tracked until git rm --cached removes it from the index.

Data out of the repository is also a data-protection point: personal or classified data has rules on where it may be stored, and a repository is copied to every laptop that clones it. The course's data is synthetic, but the habit is the point.

Where the data comes from

The code asks where the data is; the README says where to get it

ap.add_argument("--data", default=os.environ.get("VISITS_DIR"))
...
if not args.data:
    print("error: give --data <folder> or set VISITS_DIR", file=sys.stderr)
    return 2
  • No default path that exists on one computer only
  • A clear stop beats a silent empty result

The same pattern as counts.sh on Day 1, now in Python. In the report project the variable is AIR_LOGS.

One command

One documented command rebuilds, runs and checks

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"
: "${VISITS_DIR:?set VISITS_DIR to the folder of visit logs}"
uv sync --locked --quiet
uv run --quiet python planner.py --data "$VISITS_DIR" --out output
sha256sum -c expected/march.sha256
The last line is the test. sha256sum -c prints OK or FAILED and sets the exit code.

Each line is something from the last two days: the script's own folder, a required variable, the lock, the run, the check. A make target or a task runner does the same job; one shell script is the smallest version.

Watch out: an apostrophe inside ${VAR:?message} breaks the quoting in Bash. It happened in this course's first draft.

Did it reproduce?

A checksum turns "it ran" into "it gave the same bytes"

  • Running without an error proves little: an empty input also runs
  • A checksum of the expected output, committed, is a precise answer
  • When it fails, compare the first rows to see where the difference starts
  • Outputs that hold a date or a random number need those fixed first
64
hexadecimal characters in a SHA-256 checksum: one changed byte changes them all

The report project writes the same bytes on every run because its rows are sorted, numbers are formatted to one decimal, and line endings are fixed. Ask what would break that (a timestamp in the output, an unsorted dictionary from an old Python).

A Reproduce section answers four questions and assumes nothing

The four answers

  • Which tools, and which versions at least
  • Where the data comes from
  • The one command
  • What success looks like

What a peer cannot know

  • A folder on your laptop
  • A package you installed once
  • A variable in your shell profile
  • A step you always do without thinking

The capstone rubric gives 20 of 100 to the README and 30 to the peer's clean rebuild. The only honest test of a README is someone else following it on a clean machine: that is the capstone day.

Session 2

Images, containers and volumes

  • Tell an image from a container and a layer from a mount
  • Write a short container definition that installs from the lock
  • Run a container without administrator rights with data mounted read-only
02
Two words

An image is a packed file system; a container is one run of it

Image

Built once from a definition: a base system, your packages, your code, in layers. Read-only.

Container

A process started from an image, with a thin writable layer that disappears with --rm.

Volume or bind mount

A folder from outside, mounted in: where data comes in and results go out.

It is still a process. Docker's own explanation: "every container on a machine shares that machine's kernel".

Sources: Docker, What is a container; Docker, Bind mounts. Keep the kernel point for session 3: it is what a container does not isolate.

A short definition

Six instructions describe the whole image

FROM docker.io/library/python:3.13-alpine
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --require-hashes -r requirements.txt
COPY planner.py .
ENTRYPOINT ["python", "planner.py", "--data", "/data"]
  • requirements.txt is exported from the lock, with hashes: uv export --frozen --format requirements.txt
  • Packages before code: a code change reuses the cached package layer

The lab's definition adds a user that is not root and an output folder. The python:3.13-alpine image is about 17 MB compressed for amd64 on Docker Hub (read on its tags page in November 2026); pull it on the provided workspace before the session. uv's documentation recommends against keeping both uv.lock and a requirements.txt in step by hand: the export is generated from the lock, never edited.

Layers and the cache

Each instruction is a layer, rebuilt only when it or one above it changes

FROMthe base image, pulled once
↓
COPY requirements.txt, RUN pip installchanges when the lock changes
↓
COPY planner.pychanges with every code edit

Ask what happens if the definition copied the whole folder before installing: every code change would reinstall every package. The stretch of lab 3.2 shows it.

Data in, results out

Mount the input read-only and the output writable

podman run --rm \
  -v "$PWD/visits:/data:ro" \
  -v "$PWD/output:/out" \
  visit-planner
  • The image never holds the data, so one image serves every month
  • :ro means a bug cannot change the raw logs (Docker: "prevent the container from writing to the mount")
  • Results appear on your disk because /out is your folder

On Git Bash for Windows, path conversion rewrites /data; put MSYS_NO_PATHCONV=1 before the command. Source: Docker, Bind mounts.

No administrator rights

A rootless engine runs containers as you, inside a range of user ids lent to you

  • Podman is rootless by design; it needs a range of user ids for you in /etc/subuid and /etc/subgid
  • Docker rootless mode runs the daemon and containers as a non-root user
  • "root" inside the container is your own user outside, not the machine's root
  • podman run --userns=keep-id maps your user id to the same id inside

On the provided workspace

The trainer has set up the user id ranges and pulled the base image. On a laptop without administrator rights, this is the place to do lab 3.2.

Sources: Podman rootless tutorial ("requires the user running it to have a range of UIDs listed" in subuid and subgid); podman-run, --userns=keep-id; Docker, Rootless mode. Setting up the ranges needs an administrator once, which is why the course provides the workspace.

Checkpoint

Why does the report appear on your disk?

You run the planner image with -v "$PWD/output:/out" and --rm. The container is gone afterwards, yet output/plan.csv is on your disk. Why?

--rm copies the container's files out before deleting it
The file was written into the image
/out inside the container is your own output/ folder, mounted
The engine syncs every container folder back to the host
Why. A bind mount puts a host folder at a path inside the container, so writes there land on the host and outlive the container.

Session 3

What a container shares

  • Name what a container shares with its host
  • Read a key from the environment and stop clearly when it is missing
  • Keep the key out of the output and the repository, with an example file in its place
03
What a container shares

A container isolates a process, not everything around it

Shared with the hostWhat it means
The kernelA kernel flaw reaches every container; it is not a virtual machine
Every mounted folderThe container can read, and without :ro change, what you mount
Every variable you pass--env-file .env hands the key to whatever runs in the image
The network, by defaultThe program can reach what your machine can reach
The image's contentsAnyone with the image can read a key that was copied into it

The rule that follows: pass in only what the program needs, mount read-only where you can, and never build a key into an image. Source: Docker, What is a container.

The key in the code

A key in the code travels with every copy of the code

Where it goes

  • Every clone and every fork
  • Every backup and every image built from it
  • A screenshot of the editor in a chat
  • An assistant you pasted the file into

Where it belongs

  • The environment of the process that needs it
  • A .env file that git ignores, on one machine
  • The host's or the workplace's secret store

The same goes for an SSH private key from Day 1. The responsible-use rule of the course: nothing secret, personal or classified in a repository, ever.

Reading it from the environment

Read the key from a variable, stop clearly without it, and never print it whole

def booking_key() -> str:
    key = os.environ.get("VISITS_BOOKING_KEY", "")
    if not key:
        print("error: set VISITS_BOOKING_KEY (see .env.example)", file=sys.stderr)
        raise SystemExit(2)
    return key

key = booking_key()
print(f"booking with the key ending ...{key[-4:]}")

A booking-service key for the field-visit planner, not the portal key of the lab. Ask why the default is an empty string and not a placeholder key: a placeholder that looks real gets committed and copied.

Two files

.env holds the value and stays home; .env.example holds the name and is committed

VISITS_BOOKING_KEY=
.env
.env.*
!.env.example
git check-ignore -v .env                   # proves the rule matches
uv run --env-file .env python planner.py   # loads .env for this run only

The course's repository template ignores .env and .env.* and keeps .env.example: the same three lines. uv run --env-file reads the file for one command; nothing is exported to your shell.

Checkpoint

What does --env-file still expose?

You run a planner image with --env-file .env; the key is no longer in the code or the image. Who can still read the key?

Any program running in that container, and anyone who can inspect it
Nobody: variables passed at run time are encrypted
Anyone who pulls the image from the registry
Nobody, because /data is mounted read-only
Why. The variable is part of the running container's environment: its processes read it, and so can anyone allowed to inspect that container.

Answer: A. The point: the environment is the right place, and it still needs only trusted code and only the key that program needs.

Session 4

Scanning, and after a leak

  • Run a secret scan over files, staged changes and the whole history
  • Carry out the leak response in order: rotate, clean, report
  • Install a commit hook that refuses a commit holding a key
04
Scanning

Scan three places: the files, the next commit, and the whole history

Files

What is in the folder now. Clean files can still have a dirty history.

The next commit

A hook runs the scan on staged changes and refuses the commit.

The history

Every commit on every branch: what anyone who clones can read.

Tools: gitleaks (gitleaks git scans a repository's history), run from pre-commit; hosts add their own: GitHub push protection "blocks pushes that contain secrets", GitLab has secret push protection.

The course's lab uses a small scanner of its own (tools/scan_secrets.py) because it runs on every laptop without a download; gitleaks is the tool to use at work. The gitleaks README says the project is feature complete and its author's attention has moved to a successor: check the state of the tool before adopting it. Sources: gitleaks; GitHub, Push protection; GitLab, Secret detection.

Rules

Default rules know public key formats; your own keys need your own rule

[extend]
useDefault = true

[[rules]]
id = "booking-service-key"
description = "Key of the visit booking service"
regex = '''vbk_[a-z]+_[0-9a-f]{24}'''
keywords = ["vbk_"]

The shape follows the gitleaks README: extend the default rules, then add one rule per key format your organisation issues. The keyword is a cheap filter before the regular expression runs. The lab's repository ships the same kind of rule for the portal keys.

Before each commit

A pre-commit hook stops the key before it enters history

repos:
  - repo: local
    hooks:
      - id: secret-scan
        name: secret scan
        entry: uv run --no-project python tools/scan_secrets.py --staged
        language: system
        pass_filenames: false
  • uvx pre-commit install once per clone; every git commit then runs the scan
  • A hook lives in your clone only: the host's push protection is the second net

pre-commit's page: after pre-commit install, "pre-commit will run automatically on git commit". It refuses to install when core.hooksPath is set (some company laptops set it); the lab gives a plain hook as the fallback. Verified when the course was built with pre-commit 4.7.0.

After a leak

Rotate first, then clean the history, then report

1 · Rotaterevoke the key where it was issued; issue a new one
→
2 · Cleanrewrite every commit that holds it; force-push
→
3 · Tellthe key's owner and the data protection officer; check the access log
→
4 · Preventthe hook, the rule, push protection
Why rotation comes first. GitHub's guidance: "as a first step you need to revoke and/or rotate that secret". Cleaning cannot reach the copies already made.

Source: GitHub, Removing sensitive data from a repository. The duty to rotate and report is part of the course's responsible-use statement; the rotation note of the lab records it.

Cleaning the history

git filter-repo replaces the value in every commit, and every id after it changes

printf '%s==>REMOVED\n' "$OLD_KEY" > ../replacements.txt    # outside the repository
uvx git-filter-repo --replace-text ../replacements.txt --force
git remote add origin <the hub>          # filter-repo removes it on purpose
git push --force origin main
  • "Rewriting history will change the hashes of the commits" (GitHub): every teammate clones again
  • The scan of the whole history must come back clean, on your clone and on the hub

The replacements file holds the old key, so it lives outside the repository and is deleted afterwards. --replace-text takes literal text by default, with ==> and a replacement (filter-repo's manual). Hosts may keep cached views or pull request references of old commits: their documentation says how to ask for those to be removed.

Checkpoint

What do you do first?

A scan of the planner's history finds a booking-service key in a commit from three weeks ago. The repository has been public since. What is the first action?

Rewrite the history with git filter-repo
Delete the file in a new commit
Make the repository private
Revoke the key at the booking service and issue a new one
Why. Only revoking makes every copy of the old key useless; cleaning and reporting follow.
